# 上游错误提示、日限额与账号优先级修正

## PR #24 审查结论

2026-10-17 核实：<https://github.com/xiaofan6ya/workbuddy2api/pull/24> 存在，状态为 open，非草稿，GitHub 报告可无冲突合并。审查的 head 为 `60c6c7d2a024f430cfa670c1cebde62cf41d40be`，目标分支为 `master`。

问题成立，但不能原样直接合并：

1. 单条和批量重复导入在调用 `_apply_meta` 之前就覆盖了 `auth_json`，PR 新增的“凭据发生变化”判断在这两个入口始终为假。
2. PR 只清 `cool_kind`，没有清登录失效对应的 `cool_until`；已经因登录失效自动停用的账号也没有恢复路径。
3. 直接比较 JSON 字符串会把缩进、字段顺序或账号昵称变化当成更换凭据。

1.0.5 采用了 PR 的共享跳过原因文案方案，并补齐上述入口：先比较解析后的 `auth`，再写入；变化时清理旧登录失效判断和对应冷却；经过上游验证的新凭据可以恢复因会话失效自动停用的账号。手动停用保持有效。未执行 GitHub 远端 PR 合并。

## 客户端取证与错误提示

取证目录为本机已解包的 `app_source`，其 `.extracted` 标明来源是 `D:\WorkBuddy\resources\app.asar`。

- CLI 枚举、错误分类：`cli/dist/codebuddy-lite-wb.mjs`。
- 客户端中文提示：`renderer/assets/zh-cn-C7BTHfrQ.js`，SHA256 为 `d0207fbd7a9f23b5833d215f0feadc59a3ea8bfe2a5b03cd81e866963089b6ef`。
- 已提取 147 个错误码的客户端提示及说明，保存为 `admin/data/upstream_error_messages.json`。Windows 和 Android 打包均携带该文件。

| 业务 code | 客户端含义 | 本网关处理 |
| --- | --- | --- |
| 6004 | `CraftRateTPDLimit`，当前模型每日 Token 上限 | 只限制对应账号 × 模型；优先上游恢复时间，缺失时默认保守等待 24 小时，并明确标为本地估计 |
| 6008 | `CraftRateRPDLimit`，每日请求数上限；中文说明“次日零点重置” | 只限制对应账号 × 模型；优先上游时间，缺失时按北京时间次日零点恢复重试资格 |
| 6000–6003、6005–6007 | 秒 / 分 / 小时级速率或用量限制 | 与每日限制分开处理 |
| 14003 | 请求过于频繁 | 短时退避，不称为日额度耗尽 |
| 6020–6022 | 模型排队 | `retry_after` 是重试间隔，不承诺排队结束 |
| 11102 | 模型未接入或缺少服务配置 | 模型不可用，不推断为日限或凭据伪造；业务码优先于 HTTP 状态 |
| 14019 | `UsageLimitNoTokenBudget` | 补入明确用量 / 积分限制分类 |
| 401 / 402 / 3004 | 客户端对应上游身份或凭据错误 | 与工作台本地会话、本网关 API Key 鉴权分开 |

界面与最终错误返回区分三层：本网关判断、客户端对应解释、上游实际证据。保存上游 HTTP、业务 code、message、displayMsg 和原文；不再只保留 255 字符的截断原因。上游原文以文本显示，防止其中的 HTML 被执行。

上游没有给出具体每日额度数值时，限额总数与剩余数显示“未知”。本网关请求 / Token 不是官方日额度，也不覆盖客户端的消耗。历史已截断的原文无法还原；后续错误会保存完整收到的诊断内容。

## 统计与真实选号

- 修复今日统计遗漏 `error_kind=''` 的历史成功记录；同时统计 `success`。缺少 Token 记录时显示“未记录”。
- 额度不足不再宣称官方一定在次日 04:00 恢复；优先采用上游恢复时间，否则仅使用本地保守重试期限。
- 账号到期排行新增上移、下移和恢复自动排序。确认后才保存，且有服务端确认检查与过期排序检查。
- 手动优先级写入账号记录，参与真实选号，优先于自动到期策略、免费模型均衡和会话粘性。健康过滤、账号独享绑定、在途容量和模型冷却继续生效。
- Windows / Android App 继续免填后台账号密码；并发面板请求共享本地通道凭据准备，失效时自动刷新，不跳回人工登录。
