# 2api 增量可行性与风控监测调度加固

核对日期：2026-10-14。以本项目现有代码和 `app_source-architecture-review.md`
为输入，仅评估协议反代和账号池运维。原报告中的“只分析、不落地”是该报告的
历史约定；本次开发依据用户明确提出的“可行、没问题可以加进去”。

## 可行性取舍

| 原报告建议 | 对 2api 的结论 | 本轮处理 |
| --- | --- | --- |
| 7.1 符号索引、8.9 升级兼容性金丝雀 | 离线协议锚点和版本差异核对有价值；完整打包符号索引不属于请求热路径 | 保留为后续离线开发工具；已有 `wb_asar.py` 可读取/检索产物，无需另造 CLI 运行时 |
| 7.3 模型能力矩阵 | 能力与倍率可用于发现和投影，但静态 product 配置不等于当前账号资格 | 已有 `upstream_compat._normalize_one` 和 `converter.list_models` 提供上下文、输出、图片、工具、推理信息；本轮不自动删历史、压缩上下文或改费用 |
| 7.4、8.3 限流与排队调度 | 收益最高：尊重官方恢复时刻，账号×模型隔离，限制重试放大 | 加固明确恢复时间和恢复依据；沿用现有排队/每日额度隔离及跨模型尝试预算 |
| 8.5 账号健康、节奏与风控观测 | 可做基于真实响应的保护和后台节流；请求间隔/模型熵不足以推算官方风控分数 | 新增近 15 分钟被动观测、后台账号预留、统一节流和 WAF 顺延 |
| 8.7 用量洞察 | 已有使用记录、模型健康、TTFB/总耗时分位数，直接深化即可 | 在已有健康 API 和冷却弹窗补保护观测；不额外请求上游遥测 |
| 8.8 多端点自动降级 | 同域不同部署的资格/鉴权未证实等价；401 也可能是凭据或产品不匹配 | 不自动轮换官方域名、staging 或企业端点；保留显式 BACKEND 配置 |
| 7.5、8.4 成长任务 | 当前已有独立成长任务/计划模块，不是反代调用链的前置条件 | 保留现有工作，不再扩展成新的任务平台 |
| 7.2、7.6–7.10、8.1–8.2、8.6 | 官方客户端注入、A2A、CLI daemon、沙箱、连接器、本地模型托管属于 agent 平台方向 | 不纳入本次 2api 加固 |

**排队语义纠正：**现有证据支持 `6020/6021/6022` 的 `retry_after` 是下一次
重试/轮询间隔。尚无排队凭证、队列身份连续性或兑现机制的契约，不能将它命名为
“凭证 TTL”，也不能把 queue_position/queue_size 换算成可靠的预计完成时间。
本轮继续按账号×模型暂时避开排队请求；显示的是可重试时刻，不保证排队已经结束。

## 本轮实现

### 恢复时间

`admin/routers/proxy.py`：

- 明确的账号限流、模型繁忙 reset/Retry-After 不再被 120 秒或 2 小时的本地
  退避上限截短。缺少有效未来时间时仍采用已有保守退避。
- 对异常超远的上游时间保留 7 天边界，与已有日额度/排队保护一致。
- 新的明确账号恢复时间只能延后有效冷却，不能提前解除。
- 模型限流保留 `[upstream]` 恢复依据；更短的后续瞬时错误不会将依据改成本地
  退避。管理界面显示“上游明确重置时间”。

### 后台调度

`admin/maintenance.py` 与 `admin/pool.py`：

- 后台只预留空闲账号身份，预留期间对话不能获得该身份的在途租约；对话已有
  在途租约时后台直接跳过，不等待对话结束。并发上限设为 0 时此互斥仍生效。
- 接入保活、余额刷新、积分明细刷新、模型目录同步、模型繁忙度采集。
- 这些操作共享一个后台执行锁和账号间隔，默认复用
  `ADMIN_KEEPALIVE_ACCOUNT_GAP=0.8` 秒；在前一账号操作结束后计算间隔。
  0 可关闭间隔，单次间隔最多 60 秒。对话路径不增加等待。
- 节流等待发生在预留账号之前，等待期间到达的对话优先取得账号，后台随后跳过。
- 预留后重读账号凭据和状态；等待节流结束后再次检查保护。异常、返回或跳过
  都释放预留和执行锁。
- 跳过禁用、已知登录失效、账号冷却/熔断/降权、在途占用或后台竞争的账号。
  只因某个模型受限不会阻止无关的账号资料维护。
- 后台遇到 WAF、账号限流或授权限制时接入对话的既有保护策略。
  保活不会将账号授权限制直接误判为登录态失效并禁用。
- 两个不同账号的 WAF 观测触发已有出口闸门后，后续后台账号停止探测。
  定时与手动任务在保护期顺延，保持原 `last_run_at`，不会记成一次成功执行。
  闸门最后不足 1 秒时仍报告 1 秒，避免状态与倒计时相互矛盾。

跳过的账号会在下一次原定任务周期尝试；本轮没有新增每分钟全池强制保活。
保护在批次中途触发时，已完成账号不会为“补跑”而立即重复刷新。

### 监测

`GET /api/stats/model-health` 增加 `risk` 字段，后台“模型额度与冷却”弹窗同步展示：

- 近 15 分钟本网关的 WAF、账号限流、模型限流/排队、授权限制、登录失效次数；
- API 还提供各分类涉及的不同账号数、保护是否激活及剩余时间；
- 当前后台预留账号数、进程启动以来按原因累计的保护跳过次数和节流配置。

观测从已有 UsageLog 和本地保护状态读取，不新增上游模型调用，也不返回 token、
设备指纹或凭据。模型限流/排队沿用现有 UsageLog 的 `model_rate` 分类；具体
业务码仍查看账号×模型冷却记录。它不是官方风控分数，也不是官方剩余日配额。

## 验证与限制

新增 `tests/test_risk_scheduling.py`，覆盖恢复时间不截短/不回退、异常时间边界、
16 路竞争下账号预留互斥、无限并发配置下互斥、在途与冷却跳过、异常释放、
统一节流后的保护复查、后台 WAF 中止后续保活、授权限制不误禁、定时顺延、
刷新跳过、繁忙度页面停止探测、被动统计和最后一秒倒计时。
还覆盖手动运行任务的保护顺延，以及批次预留后读取最新凭据。

回归范围包含 `test_queue_busy`、`test_model_limits`、`test_account_automation`、
`test_growth_plan`、`test_gateway_hardening`。三协议流式/非流式日额度换号仍通过。
旧 hardening 测试使用已弃用的 `_valid_key_id` mock，已对齐当前
`_key_admission_params` 和 `allow(key, rate, concurrent)` 契约，避免真实查库和挂起。
管理页内联脚本通过 Node 语法校验。

本轮上述 7 个测试文件共执行 102 项：100 项通过，2 项 Redis 测试跳过；
其中新增调度回归 17 项全部通过。Python 编译与 `git diff --check` 通过。

全部验证使用模拟上游和隔离 SQLite；没有进行线上发布、真实模型消耗、
登录态刷新或出口 WAF 探测。fakeredis/lua 未安装时两项 Redis 测试明确跳过。

账号预留、后台执行锁、WAF 状态、跳过累计目前仍为**进程内**；持久冷却仍在
数据库。多 worker / 多实例需要共享账号租约与出口闸门后才能保证全局一致。
其他手动管理操作、登录后收尾、成长计划内部请求尚未全面接入账号预留，
因此本轮不声称所有账号凭据写入均已全局串行化。
